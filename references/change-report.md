# 模式 B:改动汇报

把一次任务的全部代码改动,变成一页任何人都看得懂的东西:**改了什么 · 动了哪些表字段 · 改了哪些原有业务规则 · 影响哪些业务点 · 出事怎么回滚。**

产出一份:`<BASE_URL><slug>_changes/?v=N` —— HTML 一页,给人看。

---

## 0. 先立底账(这一步不做,后面全是假的)

```bash
BASE=$(git merge-base HEAD origin/develop)     # 或用户指定的基线
git diff --stat $BASE...HEAD | tail -1          # 总数
git diff --name-status $BASE...HEAD > /tmp/cr_ledger.txt
wc -l < /tmp/cr_ledger.txt                      # 底账文件数 N
```

工作树里还有未提交改动时,底账要合并 `git status --porcelain` 的结果。

**这份 `cr_ledger.txt` 是唯一底账。**报告最后必须能对上:底账 N 个文件,报告覆盖 N 个文件,一个不少。没动业务规则的文件也要出现在 §2 清单里,标「无规则影响」,不能沉默跳过。

## 1. 六条线并行采集

六个代理同时跑,互不依赖。每个只干一件事,返回结构化结果,主线程汇总。

| 线 | 干什么 | 输出 |
|---|---|---|
| L1 清点官 | 逐文件过 diff,给每个文件一句话定性 | 文件清单 + 是否触及业务规则 —— **喂给 S1 的 ASCII 树做注释**,不再单独列表 |
| L2 数据库 | 迁移、建表、改字段、索引、seed | 表字段变更表 + 兼容性 + 回滚 SQL |
| L3 **规则比对** | **逐行**看,每行回答「动了哪条原有规则」 | 规则变更卡(原→新→触发条件→受影响方) |
| L4 影响面 | 每个改动符号的调用方、被哪些端用 | 影响矩阵(端 × 角色 × 场景) |
| L5 接口 / 文案 | API 契约变化、i18n key 增删改、多语言补全 | 契约 diff + i18n 缺 key 清单 |
| L6 风险 | 测试覆盖、并发 / 事务 / 幂等、回滚步骤 | 风险表 + 验证清单 |

L3 是主菜,文件多时按目录再拆几个代理(如 `controllers/` 一个、`service/` 一个、`model/` 一个),但**每个代理拿到的必须是完整 diff 片段,不是摘要**。

派发时注意:

- **代理名只能用 ASCII**(`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`),写 `L1-清点官` 会被直接拒掉。用 `L1-inventory`、`L3a-merge-core` 这种。
- 八条线一次性发出去(同一条消息里多个 tool use),不要一条条等。
- 每条线的 prompt 里都要写死三件事:**基线 commit 表达式**、**它负责的完整文件清单**、**「不许只看 --stat 下结论」**。少写一条,回来的就是摘要级废话。
- 明确告诉每个代理「你的最终文本就是返回值」,否则它会写一堆寒暄和过程叙述。

### 分工提示词模板

L1 清点官:

> 基线 `<BASE>`。跑 `git diff --name-status <BASE>...HEAD`,对每个文件跑 `git diff <BASE>...HEAD -- <file>` 读完整 diff。
> 每个文件返回:path / 变更类型(新增·修改·删除·重命名) / 增删行数 / **一句大白话说它干了什么**(不要抄函数名,说业务动作) / 是否触及业务规则(是·否·待定)。
> 覆盖底账里每一个文件,不许跳过配置、生成文件、测试。生成文件标注「生成物,随 xx 变更」。
> 返回 JSON 数组。

L2 数据库:

> 找出本次所有数据库相关改动:`admin/database/migrations/`、`seeds/`、model 的表结构定义、gorm/GoFrame tag、SQL 字符串里的 DDL。
> 每个字段返回:表名 / 字段名 / 动作(新增·改类型·改默认值·改可空·删除·加索引) / 旧定义 / 新定义 / 是否可空 / 默认值 / 存量数据怎么办 / 回滚 SQL。
> 同时给:是否有大表 DDL 锁风险、是否与代码上线顺序耦合(先加字段还是先发代码)。
> 没有数据库改动就明确返回空数组,不要猜。

L3 规则比对(核心):

> 目标目录 `<dir>`。对其中每个改动文件跑 `git diff <BASE>...HEAD -- <file>` 拿到完整 diff,**逐行**分析。
> 对每一处 `-`/`+`,回答:这行原来的业务含义是什么、改成什么、什么条件下才走到这里、结果对谁可见(用户·门店·财务·报表·下游服务)。
> 只输出**规则级**变化(判断条件、阈值、状态流转、金额算法、权限校验、默认值、排序口径、时间窗口、幂等键、错误分支)。
> 纯重命名、格式化、提取函数但语义不变的,归入 `no_rule_change` 并列出文件,不要编造影响。
> 每条规则变更返回:rule_id / 一句话标题 / 原规则(引用旧代码行) / 新规则(引用新代码行) / 触发条件 / 受影响方 / 代码位置(file:line) / 风险等级(高·中·低) / 是否向后兼容。
> **禁止只读 diff 摘要或 --stat 就下结论。**不确定时把该行标为 `uncertain` 并说明要确认什么,不要蒙。

L4 影响面:

> 对 L1 标为「触及业务规则」的每个符号(函数·方法·接口·常量),用 rg 找出全部调用方,判断被哪些端用到(pos·shop·kds·qds·assistant·tablet·kiosk·web menu/mobile/member·admin·bmp·定时任务·对外 API)。
> 返回:符号 / 调用方文件 / 所属端 / 触发场景(用户在哪一步会碰到) / 是否高风险区域(payment·order·cart·checkout·handover·api 拦截器·model 金额相关)。

L5 接口 / 文案:

> 1) 找出 API 契约变化:新增/删除/改名的路由、请求字段、响应字段、状态码、错误码。标出是否 breaking、老客户端会怎样。
> 2) 找出所有面向用户的新增/修改文案,检查翻译文件是否补齐:
>    Flutter `packages/i18n/lib/langs/*.dart` 共 10 个 locale;
>    Go main `main/i18n/languages/*.json` 共 9 个;
>    admin `admin/lang/{locale}/`。
>    返回缺 key 的 locale 清单。日志、内部错误堆栈不算。

L6 风险:

> 结合改动范围给出:1) 有没有对应测试、跑没跑过、结果;2) 并发·事务·幂等·超时·重试上的隐患;3) 数据迁移与代码上线的先后顺序;4) 逐步回滚步骤(代码回滚 + 数据回滚,分开写);5) 上线后要盯什么指标 / 日志关键字。

### 汇总时怎么处理代理的结论

- **结论打架不要合并,去复核。**两条线对同一件事给出不同答案时,那处往往两边都只说对一半 —— 自己读那几行代码,得出的经常是第三种结论。实战里出现过:一条说"全走只读池"、一条说"走主库",复核发现是"读池设了,但被中间某次调用 `ctx.SetDB()` 覆盖了",这条成了报告里的高风险项。
- **被证伪的怀疑也要写进报告。**你在 prompt 里让代理重点查的东西,查完不成立,就写一句"查过,不成立,原因是 X"。否则读者不知道你查没查,还得自己再查一遍。
- **代理主动纠正你的用词就采纳它。**prompt 里的业务命名可能是错的(实战里把外送/外卖写反过),代理去代码里核过表名和注释,以它的为准。
- 交叉验证是免费的置信度:同一条问题被两三条线**独立**定位到同一行,报告里点出来,读者知道这不是单点臆测。

## 2. 八节骨架

**先把正文栏切到报告档。**改动汇报的主体是规则卡 + 表与字段 + 并排双栏,不是散文,900px 装不下,而且紧邻的 `.bleed`(1440px)会形成一倍宽的断层:

```html
<div class="wrap rep">   <!-- 1280px。模式 B 一律加 rep,见 SKILL.md §7 宽度 -->
```

改已有页面用 `python3 assets/align-page.py <页面> --report`。


每节**先一句大白话结论,再上表格和图**。别让读者自己从 diff 里悟。

| 节 | 标题 | 内容 | 主要形态 |
|---|---|---|---|
| S0 | 一句话说清 | 这次到底干了什么、为什么、上线后用户能感觉到什么 | 大白话 3~5 行 + 关键数字条 |
| S1 | 改动全景 | 仓库 → 模块 → 文件的树,带增删行数 | **ASCII 树** |
| S2 | 表与字段 | 动了哪些表、哪些字段、存量数据怎么办、回滚 SQL | 表格 + ASCII 字段树 |
| S3 | **业务规则改动** | 每条一张卡:原规则 → 新规则 → **页面 / 操作 / 结果** → 谁受影响 → 代码位置，**每卡下面配一帧画出来的页面** | 规则卡 + 界面帧(★ 全篇最重) |
| S4 | 流转与调用链 | 状态机怎么变的、请求怎么走的 | **mermaid 黑底** |
| S5 | 影响面矩阵 | 端 × 角色 × 场景,谁会碰到 | 矩阵表(积木 E) |
| S6 | 接口与文案 | API 契约 diff、i18n 补全情况 | 双栏对照(积木 F) |
| S7 | 风险 · 回滚 · 验证 | 风险等级、回滚步骤、验证清单(可勾) | 三色要点卡(积木 G) |

界面有变化时,在 S3 对应规则卡下面插一帧界面(积木 F 并排双栏:改前 / 改后),比文字快十倍。

### S3 规则卡的固定格式

**「用户视角」三行是必填项**,不是可选的。写不出来说明你还没搞清这条改动对谁有影响。

```
R3  超过 30 天的订单不能再退款
────────────────────────────────────────────
原规则   下单后任意时间都可发起退款
         order_service.go:184  if order.Status == PAID
新规则   下单超过 30 天禁止退款,提示「已超过退款期限」
         order_service.go:184  if order.Status == PAID && time.Since(order.PaidAt) <= 30*24h
─── 用户视角(必填) ──────────────────────────
页面     POS 收银 › 订单详情(已支付订单)      <- 下面必须配一帧画出来的界面
操作     收银员点底部「申请退款」按钮
结果     改前:直接进入退款流程,可退
         改后:弹「已超过退款期限」,按钮置灰,退不了
─────────────────────────────────────────────
受影响方 门店收银(拒绝提示) · 财务(退款单量下降) · 顾客(H5 看到新提示)
风险     中 —— 存量超期订单的退款诉求要走人工;文案需 10 语言
兼容性   不向后兼容:老客户端不认新错误码 40031,会显示原始 message
```

**每张规则卡下面必须插一帧页面**,用积木 F 并排双栏(改前 / 改后),或单帧 + `.newf` 绿框标出变化处。手机端用 `.phone`,后台页用 `.shell`,列表用 `.dt`,小票用 `.rcpt`。

**用户侧真的无感知时**(纯性能优化、纯重构),照样要写这三行,内容是:

```
页面     门店后台 › 订单管理 › 用餐订单(跨店视图)
操作     总部账号点页脚「最后一页」
结果     改前:内存峰值 ~557MB,极端情况进程 OOM,页面转圈后报错
         改后:同样操作,内存 ~29MB,正常出数据;返回内容一致
         用户可见行为无变化,变的是能不能扛住
```

**禁止**只写"用户无感知"就跳过 —— 那是在回避"到底谁会走到这条路径"这个问题。

HTML 里用 `.rule` 卡片(积木库里有),原规则灰底、新规则绿框、风险红字,用户视角三行用 `.hint` 块或独立 `<dl>` 突出。

## 3. 图怎么画

### ASCII —— 结构和清单

只用半角。表名、字段名、文件名本来就是英文;中文说明放框外或右侧 `#` 注释列,不参与对齐。包在 `<pre class="ascii">` 里。

```
backend-repo
  main/app
    ├─ service/order_refund.go      +48 -12   ★ 规则 R3 R4
    ├─ controller/order.go          +9  -2      错误码透传
    └─ model/order.go               +3  -0      新增 refund_deadline_at
  admin/database/migrations
    └─ 20260813_add_refund_deadline.php  +21   ★ 表结构
frontend-repo
  apps/pos/lib/controllers/order
    └─ refund_controller.dart       +16 -5    ★ 规则 R3(客户端预校验)
  packages/i18n/lib/langs
    └─ *.dart  ×10                  +10       新增 refund_expired
```

### mermaid —— 状态流转和调用链,**全篇唯一用黑底的地方**

页面整体浅色,mermaid 卡黑底,一眼跳出来。因为不能引 mermaid.js,先写**深色源码卡**,页面收尾**必须**跑渲染器把它变成真正的图。每张图第一行必须带主题:

```
%%{init:{'theme':'base','themeVariables':{'background':'#0b0f14','primaryColor':'#111827','primaryTextColor':'#e5e7eb','primaryBorderColor':'#334155','lineColor':'#64748b','secondaryColor':'#1e293b','tertiaryColor':'#0f172a','fontFamily':'ui-monospace,SFMono-Regular,Menlo,monospace'}}}%%
stateDiagram-v2
    [*] --> PAID
    PAID --> REFUNDING : 申请退款(≤30天)
    PAID --> REJECTED : 申请退款(>30天) 【本次新增】
    REFUNDING --> REFUNDED : 网关回调成功
```

变化的边 / 节点在标签里写「【本次新增】」「【本次修改】」,黑底里不好用颜色区分就用文字标。

**收尾必跑**(SVG 是纯文本,内联不破坏单文件约束,也不需要 CDN):

```bash
python3 ~/.claude/skills/html-mockup/assets/render-mermaid.py ~/www/<页面>/index.html
grep -c '<svg' ~/www/<页面>/index.html      # 要等于 .mmd 卡片数
```

只贴源码不渲染 = 读者手机上看到一坨代码,等于图没画。渲染器会把源码收进 `<details>` 折叠(仍可复制到 issue / PR),并按 viewBox 宽度分档:>900px 的宽图保原尺寸 + 横向滚动,不压成蚂蚁字。

### preview_html —— 默认形态

单张规则卡、一句话结论 + 数字条、单张 mermaid 黑底卡、几节内容,**直接 `preview_html`**,不要因为"有点长"就预先绕道 8008。

**改动汇报整份报告仍然走 8008**,但原因不是"太长",而是命中了 SKILL.md §4.5 的 ①②:它要贴给评审人看、要能 `?v=N` 改版、要有个能回头翻的链接。体量大(实测 26 文件那份 59KB)只是附带原因。

判定一律按 §4.5 那张表走,别在这里另起一套标准。

## 4. 收尾自检(五条都过才能说「完成」)

```bash
# 1. 覆盖率:底账文件数 == 报告覆盖数（直接扫产出的 HTML）
wc -l < /tmp/cr_ledger.txt
grep -oE '[A-Za-z0-9_./-]+\.(go|dart|php|ts|tsx|sql|json|yaml|yml|conf|vue)\b' <目录>/index.html | sort -u | wc -l
```

2. **规则闭环**:每条规则卡都有原规则和新规则的**真实代码行引用**(file:line),不是描述。
2.5 **用户视角闭环**:每条规则卡的「页面 / 操作 / 结果」三行都填了,且**页面真的画出来了**(不是只写页面名)。纯性能/重构类也要写,不许用一句"用户无感知"跳过。
3. **四块齐全**:表字段、业务规则、业务点影响、回滚 —— 缺一块不算完成。
4. **`uncertain` 清零或明示**:L3 标为不确定的行,要么查清,要么在报告里单列「待确认」并说明要问谁。
5. **链接可达**:`curl` 公网 BASE_URL 返回 200,且带 `?v=N`。

## 5. 交付话术

**地址必须明文完整贴出**,不要用 `[文字](url)` 藏起来(见 SKILL.md 交付话术)。

```
✅ 本次改动汇报:
   https://8008--main--<workspace>--<owner>.<你的 Coder 域名>/<slug>_changes/?v=1

   一句话:<S0 的结论>
   动了 N 个文件 / M 张表 / K 条业务规则,其中高风险 X 条(S3 红字)
   回滚步骤在最后一节
```
